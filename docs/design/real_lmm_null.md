# Real-LMM Null Path Design Note

Date: 2026-07-18

This note scopes the Release 2 random-slope null path. It is intentionally a
design and calibration record for a minimal slice, not a production backend
specification.

## Goal

Release 1 validates the fast marginal-OLS path for crossed random intercepts
under within-subject permutation, and refuses random slopes because the OLS
condition t statistic ignores subject-varying slope variance. Release 2 should
add an opt-in real-LMM null path for random slopes without changing the fast
default.

The intended null statistic is the fixed-effect condition statistic from the
same mixed model fitted at each feature and each null draw:

```text
y ~ cond + (1 + cond | subject) + (1 | item)
```

for the random-slope case, and the corresponding crossed-intercept model when no
slope is present.

## Statistic

Use the lmerTest fixed-effect t statistic with Satterthwaite denominator degrees
of freedom.

Rationale:

- The verified pymer4 0.9.2 surface exposes lmerTest output in
  `model.result_fit`, including `estimate`, `std_error`, `t_stat`, `df`, and
  `p_value`.
- Satterthwaite is the lmerTest default surface available through pymer4 without
  additional per-fit control. It is the pragmatic Release 2 statistic because it
  is already part of the verified stack and is materially cheaper than
  Kenward-Roger.
- Kenward-Roger can be attractive for small-sample pointwise inference, but it
  requires extra covariance adjustment machinery and typically more computation.
  It should be treated as a later optional statistic after a separate surface
  and calibration pass.
- The key fix for the Release 1 random-slope failure is not the exact denominator
  df method; it is replacing the marginal-OLS t with a mixed-model t whose
  standard error includes subject-level slope variance.

## Per-Feature Inference Hypothesis

Hypothesis: under the mixed-model assumptions used by the generator, the
lmerTest Satterthwaite p value is calibrated per feature for the tested fixed
condition effect. Permutation is then needed for family-wise correction across
the channel-time map, and for cluster/TFCE topology, not to rescue an invalid
per-feature statistic.

The minimal validation slice must therefore check two things separately:

- H0 generator guard: repeated random-slope datasets with zero population
  condition effect produce condition estimates centered on zero and approximately
  uniform lmerTest p values at every feature.
- Map-level null: refitting the LMM under within-subject condition permutations
  yields family-wise rejection rates near nominal for C2, while C1 remains
  nominal and C3 remains powered.

## Permutation Scheme

Use within-subject permutation for the FWER null.

Free row-shuffle remains invalid even with an LMM statistic. The condition
manipulation is within subject, so exchangeability is block-structured by
subject. A free shuffle changes the subject-level treatment pattern and creates
null draws that are not generated by the experimental randomization. The LMM
can model subject random effects in each refit, but it does not make an invalid
randomization scheme valid.

The known limitation remains: within-subject permutation respects the subject
factor but does not also constrain the crossed item factor. This is the same
pragmatic limitation accepted for the Release 1 crossed-intercept envelope. A
fully crossed randomization scheme would need a separate design-specific
exchangeability model.

## Feasibility

The real-LMM null requires one mixed-model fit per feature per permutation,
plus the observed fits:

```text
n_fits = n_sims * (n_permutations + 1) * n_features
```

For the existing tiny calibration map, `n_features = 2 locations * 2 times = 4`.
At the requested `n_sims = 300` and `n_permutations = 500`, a single C1/C2/C3
scenario requires:

```text
300 * 501 * 4 = 601,200 LMM fits
```

That count is before multiplying over maxstat, cluster, and TFCE reporting. The
same LMM t maps can be reused across correction summaries, so the implementation
must compute the observed and null t maps once per simulated dataset, then apply
all correction summaries to those maps.

A realistic EEG map is much larger. For 64 channels and 500 time points:

```text
n_features = 32,000
fits per dataset at 1,000 permutations = 32,032,000
fits for 300 calibration datasets = 9,609,600,000
```

Local timing on 2026-07-18 with the verified pymer4/R stack was measured on a
6-subject x 5-item random-slope design:

```text
8 pymer4/lmerTest fits in 16.148 s = 2.019 s per feature fit
```

At that rate, the requested tiny 4-feature, 300-sim, 500-permutation C2 cell is
approximately 14 days of serial pymer4/rpy2 fitting for the LMM t maps alone.
A single realistic 64x500 EEG dataset with 1,000 permutations would be measured
in years. pymer4/rpy2 is therefore not a viable production engine for dense
real-LMM permutation or TFCE nulls.

Recommended path:

1. Keep pymer4 as the correctness oracle and small-design validation surface.
   Use it to prove the statistic and permutation scheme on deliberately tiny
   maps.
2. For production-scale real-LMM nulls, prototype a MixedModels.jl engine through
   juliacall. The model and statistic still need their own verified surface and
   calibration, but Julia is the plausible route for dense refits.
3. Until a faster engine exists, restrict pymer4 real-LMM nulls to small
   time-window/ROI analyses where the fit count is explicit and accepted by the
   caller.

Potential refit-avoiding approximations are not recommended for Release 2. Any
approximation that reuses fitted random effects, treats BLUPs as fixed, or
updates only the fixed-effect contrast would need a separate proof of
exchangeability and calibration under random slopes. That would no longer be the
real-LMM null this note is specifying.

## API Surface

Expose this as an additive null-method or backend choice, leaving the Release 1
fast path untouched:

```python
FitConfig(
    lmm_backend_name="pymer4",
    null_method="fast_marginal_ols",  # default
)

FitConfig(
    lmm_backend_name="pymer4",
    null_method="real_lmm_refit",  # opt-in, calibration/ROI scale only
)
```

The production API should make the envelope visible:

- `fast_marginal_ols`: default; validated for crossed random intercepts under
  within-subject permutation; refuses random slopes.
- `real_lmm_refit`: opt-in; fits the full mixed model for observed and null
  condition assignments; intended for random slopes; must report fit counts and
  expected runtime before running large jobs.

Correction backends should consume statistic maps rather than refit models
themselves. That keeps maxstat, cluster, and TFCE as summaries over a shared
observed map and shared null-map stream.
